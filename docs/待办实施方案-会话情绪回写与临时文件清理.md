## 3. 待办 7：过期临时文件清理

### 3.1 现状核实：现有数据的 `is_temp` 全为 0，README 字面的清理条件永远命中 0 条

按列名精确读取 `sys_file_info`（11 行）：

| id | `file_path` | `is_temp` | `status` | `expire_time` |
| --- | --- | --- | --- | --- |
| 46-49 | `/files/bussiness/article/*` | 0 | 1 | NULL |
| 50-52 | `/files/temp/*` | **0** | **0** | 有值（2025-09-13，已过期） |
| 53-56 | `/files/bussiness/{user_avatar,article}/*` | 0 | 1 | NULL |

分组统计：

```
is_temp  status  条数  路径在 temp 目录  有过期时间
   0        0      3         3              3
   0        1      8         0              0
```

**两个关键结论：**

1. **`is_temp` 在所有 11 行中都是 0**，从未被置为 1。因此 README 第 7 条描述的筛选条件（`is_temp = 1 AND expire_time < now()`）**命中 0 条 —— 清理任务会永远什么都不做**。这才是待办 7 真正要先解决的问题：不是"写个定时任务"，而是**存量数据的 `is_temp` 语义没有被正确设置**。
2. 磁盘上（`backend/uploads/`）**没有任何文件**，3 条临时文件对应的磁盘文件并不存在。

> **注意区分代码与存量数据**：`FileStorageService#upload()` 是**正确**设置 `is_temp` 的（`businessType` 为空时置 1 并写入 `files/temp/`）。也就是说**通过接口新上传的临时文件会被正确标记**，`is_temp` 全为 0 只是这批示例数据的问题。因此清理逻辑本身是可行的，需要处理的是存量数据。

### 3.2 建议的筛选条件（防御式）

即使 `is_temp` 修正后，也建议叠加路径校验，避免脏数据造成误删：

```
is_temp = 1
AND status = 1                              ← 未被软删的
AND expire_time IS NOT NULL AND expire_time < now()
AND file_path LIKE '/files/temp/%'          ← 路径白名单
AND 该 file_path 未被 knowledge_article.cover_image 引用
AND 该 file_path 未被 user.avatar 引用
```

路径白名单的依据：`FileStorageService` 仅在 `businessType` 为空时才写入 `files/temp/`，**临时文件路径必然以 `/files/temp/` 开头**，可据此交叉验证 `is_temp` 是否可信。

**引用检查的实测情况**（供参考，非当前风险）：

- `knowledge_article.cover_image`：7 篇示例文章**全部为空字符串**，未引用任何文件
- `user.avatar`：2 条非空，分别指向 `sys_file_info` 的 id 53、55（`/files/bussiness/user_avatar/*`）
- 这 2 条记录 `is_temp = 0`、路径在 `bussiness/` 下，**本就不会被临时文件清理命中**；引用检查属额外保险

### 3.3 删除策略（已定：软删记录 + 物理删文件）

| 对象 | 处理 |
| --- | --- |
| `sys_file_info` 记录 | **软删**：`status = 0`（与现有 3 条临时文件的既有状态一致） |
| 磁盘文件 | **物理删除**（否则磁盘不释放，失去清理意义；软删记录保留审计痕迹） |

选择软删的理由：`status` 列注释本就是「0:删除 1:正常」，与既有数据一致；记录得以保留，便于追溯"哪些文件被清理过"。

**磁盘路径推导**：`file_path` 形如 `/files/temp/xxx.jpg`，而 `WebMvcConfig` 把 `/files/**` 映射到 `{app.upload.root}/files/`。故磁盘路径 = `{app.upload.root}` + `file_path`。

**文件不存在时应如何处理**：既然存量临时文件的磁盘文件已不存在，清理任务必须容忍"文件不存在"——直接**跳过删除文件、仅软删记录**，并计入"跳过"而非"失败"。

### 3.4 安全要求：路径穿越防护

删除磁盘文件前必须规范化并校验落在上传根目录内，复用 `FileStorageService` 已有做法：

```java
Path baseDir = Paths.get(uploadRoot).toAbsolutePath().normalize();
Path target  = baseDir.resolve(relativePath).normalize();
if (!target.startsWith(baseDir)) {
    // 拒绝：记录告警并跳过，不删除
}
```

即 `file_path` 若含 `../` 等穿越字符，一律拒绝。

### 3.5 调度与配置

配置项（已在前置改动中落地）：

```yaml
app:
  upload:
    cleanup:
      enabled: true        # 是否启用清理
      cron: "0 30 3 * * ?" # 每天 03:30
      batch-size: 200      # 单次最多处理的记录数
      dry-run: false       # true = 只记日志不实际删除
```

实现要点：

- `@Scheduled(cron = "${app.upload.cleanup.cron}")`
- `enabled: false` 时用 `@ConditionalOnProperty` 使该 Bean 不注册
- `batch-size` 用 `LIMIT` 限制，避免一次性删除过多
- **`dry-run: true` 只输出"将会删除哪些文件"的日志**，不做任何写操作 —— 建议首次上线先跑一轮观察
- 单条失败（文件被占用等）**不中断整批**：逐条 try/catch，记录后继续
- 汇总日志：命中数 / 已删除数 / 跳过数 / 失败数

### 3.6 可观测性

定时任务无 HTTP 入口，以**日志**为主要证据：

```
临时文件清理完成（dry-run=false）：命中 3，已删除 0，跳过 3（文件不存在），失败 0
临时文件清理跳过（已被引用）：filePath=/files/temp/x.jpg, articleId=...
```

## 4. 待办 6：会话情绪分析回写

### 4.1 阻塞点：`ai_analysis_task` 无法容纳会话任务

表结构实测：

```sql
diary_id  bigint  NOT NULL   -- 外键 fk_ai_task_diary → emotion_diary(id)
user_id   bigint  NOT NULL   -- 外键 fk_ai_task_user → user(id)
```

**`diary_id` 非空且外键指向 `emotion_diary`**，因此会话分析任务**无法写入该表**。这是 README 待办 6 说"可复用 `EmotionAnalysisService`"时未覆盖的点：日记分析能记任务，会话分析不能。

### 4.2 任务追踪的三种方案（**待决策**）

| 方案 | 做法 | 代价 | 评价 |
| --- | --- | --- | --- |
| **A** | `ai_analysis_task` 增加 `session_id` 列，`diary_id` 改为可空，加约束保证二者恰有其一 | 需 DDL 迁移；表语义扩展为通用"AI 分析任务" | **推荐**：与 README 第 1 条"失败会记录在 `ai_analysis_task.error_message`"的可观测性设计一致 |
| **B** | 会话分析不记任务表，成功回写、失败仅打日志 | 零 DDL | 最简单，但会话分析失败在管理端不可见 |
| **C** | 不记任务表，失败时把错误写入 `consultation_session` 新增列 | 仍需 DDL | 与 B 差别不大，且把错误信息混进业务表 |

**方案 A 的迁移脚本草案**（存量 9 条任务 `diary_id` 均非空，迁移无歧义）：

```sql
ALTER TABLE ai_analysis_task MODIFY COLUMN diary_id BIGINT NULL;
ALTER TABLE ai_analysis_task ADD COLUMN session_id BIGINT NULL AFTER diary_id;
ALTER TABLE ai_analysis_task
  ADD CONSTRAINT fk_ai_task_session FOREIGN KEY (session_id) REFERENCES consultation_session(id);
ALTER TABLE ai_analysis_task
  ADD CONSTRAINT chk_ai_task_target
  CHECK ((diary_id IS NULL) <> (session_id IS NULL));
```

> 迁移脚本建议放 `database/migrations/`，不改动主 SQL 文件，避免影响全新环境的初始化流程。

### 4.3 触发时机（已定）

在 `PsychologicalSupportService#streamPsychologicalChat()` 的 `.doOnComplete()` 中触发 —— 该处已 `saveAimessage(...)` 保存了 AI 回复，紧随其后触发分析。

**为什么不能照搬日记的 `triggerAnalysisAfterCommit()`**：该处运行在 Reactor 流回调线程，`TransactionSynchronizationManager` 的注册不可靠。而 `saveAimessage` 是独立提交的，因此**直接 `@Async` 调用即可**。

```java
.doOnComplete(() -> {
    String completeRes = fullResponse.toString();
    consultationMessageService.saveAimessage(dbSessionId, completeRes, "openai");
    // ... chatMemory 追加
    emotionAnalysisService.analyzeSessionAsync(dbSessionId);   // ← 新增
    sink.complete();
})
```

**失败必须隔离**：分析异常不得冒泡到流中，否则会中断 `sink.complete()`，导致前端 `isAiTyping` 卡住、输入框永久禁用。`analyzeSessionAsync` 内部需捕获全部异常。

### 4.4 分析输入

取该会话**最近 N 条消息**（建议 N = 20，避免 token 爆炸），拼接为对话文本：

```
用户：<content>
AI助手：<content>
...
```

**提示词要点**（常量 `PromptManage.SESSION_EMOTION_ANALYSIS_SYSTEM_PROMPT` 已写好）：

- 强调**只依据"用户"说的话判断情绪，忽略 AI 助手的措辞** —— 助手文本偏温暖正面，会稀释用户真实情绪
- 输出 JSON 字段与日记分析一致（便于复用 `normalize()`）
- 危机信号（自伤/自杀/绝望）→ `riskLevel` 必须为 3
- 明确要求不输出 markdown 代码块与解释文字（虽 `extractJson()` 有容错，减少对容错的依赖更好）

### 4.5 回写

```java
consultationSessionMapper.updateById(ConsultationSession.builder()
        .id(sessionId)
        .lastEmotionAnalysis(analysisJson)          // normalize() 后的 JSON 字符串
        .lastEmotionUpdatedAt(LocalDateTime.now())
        .build());
```

**接口层无需改动**：`GET /api/psychological-chat/session/{id}/emotion` 已读取这两个字段，并兼容 `session_` 前缀、有兜底默认值。

**存储格式必须是 JSON 字符串**（不是对象）：`ConsultationQueryService#getSessionEmotion()` 用 `JSONUtil.parseObj(...)` 解析，传对象会解析异常。

### 4.6 前端配合（已定：延迟重拉）

现状：`consultation.vue` 在 SSE `done`（第 396 行）与 `onclose`（第 412 行）**各调一次** `loadSessionEmotion`，都在"结束瞬间"拉取。

由于分析是异步的，那一刻**分析尚未完成**，面板会显示上一轮结果或兜底默认值。

按已定方案：`done` 之后**延迟约 1.5s 再重拉一次**。注意：

- **两个调用点都要处理**（`done` 与 `onclose`），否则行为不一致
- 延迟期间用户可能已切换会话 → 重拉前需校验当前 `sessionId` 未变，避免把 A 会话的情绪渲染到 B 会话
- 组件卸载时清理定时器，避免内存泄漏与"更新已卸载组件"告警
